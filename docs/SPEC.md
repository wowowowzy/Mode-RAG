# ModeRoute

> 一个应用层的**推理模式召回组件**：给定任务，从模式库召回最适配的「推理骨架」，以一段可直接拼入 prompt 的文本返回。
> 一句话概括：**执行者不变，变的是这一次注入的推理骨架。**

---

## 1. 项目是什么

同一个模型，问法不同，推理路径差别很大。复杂任务上"直接答"容易走偏——漏掉硬约束、只论证单边、跳步不核验。

业界的解法有两条：训练（把策略压进参数），或者路由（换模型、换 agent、换工具）。前者的代价是模式锁在黑盒里改不动，后者没有解决"同一个模型该怎么想"的问题。

本项目做第三件事：**不改模型、不换执行者，只在调用前注入一段结构化的"怎么想"。**

和 RAG 的类比最直观：RAG 检索的是「知道什么」，我们检索的是「怎么想」。检索单元从知识文档变成推理骨架，所以它可编辑、可组合、可审计、可做消融。

| 对照对象 | 它做的事 | 本项目 |
| --- | --- | --- |
| MoE | 参数层按输入激活专家 | 应用层，不碰模型参数 |
| RAG | 检索知识文档注入上下文 | 检索推理骨架 |
| Agent 路由器 | 选哪个 agent / 模型 / 工具执行 | 执行者不变，选"怎么想" |
| 推理蒸馏类工作 | 训练时把策略压进模型 | 免训练，模式可由人编辑与审计 |

---

## 2. 边界

**做什么**：一个**只有后端的 Web 服务**。启动后监听端口，暴露 HTTP 接口。输入任务文本，输出一段可拼入 prompt 的推理骨架文本 + 极简决策信息。

没有前端页面、没有静态资源、没有可视化界面。所有能力都由接口提供，调用方是别的程序。

**不做什么**

- 不调用执行模型。不持有其凭据，不产生其费用，也不知道对方用什么模型
- 不调用大模型做判断。精判交给专门的决策模型，降级时用规则
- 不训练、不微调任何模型
- 不管人设、不管插入位置、不管 prompt 组装——这些是调用方的职责
- 不做知识检索
- 无状态，不存会话、不存聊天记录

**定位**：调用方 advisor 链里的一环。它调我们拿一段文本，非空就拼进去，空就放行。

## 3. 技术选型

| 类别 | 选型 |
| --- | --- |
| 语言 | Java 17 |
| 框架 | Spring Boot 3.5.6 |
| AI SDK | Spring AI 1.1.x（BOM 导入） |
| 构建 | Maven 工程，产物是一个可 `java -jar` 启动的服务 |
| 存储 | 无数据库。卡片是文件，向量在进程内存，日志追加写 JSONL |
| 接口文档 | OpenAPI 自动生成 |

**版本代际必须对齐**：Spring Boot 3.5.x ↔ Spring AI 1.1.x。3.4.x 配 1.0.x，4.x 配 2.x。跨代际会出现自动配置类缺失。

**Spring AI 用在哪、不用在哪**

- **用**：算 embedding（召回用）。换后端只改配置，不改编排代码
- **不用**：调执行模型（产品定位禁止）；调决策模型（`/v1/systemone` 既非 OpenAI chat 也非 OpenAI embeddings 格式，没有对应抽象，手写 HTTP 更直接）

**不要引入**

- 数据库 / 缓存服务 / 向量库。48 张卡的向量约 192 KB，进程内暴力扫描是几十微秒，比任何外部组件的往返都快一个数量级。它的价值从几千条向量才开始显现
- 前端框架、模板引擎、静态页面、图表库。本项目没有 UI，图表在实验报告环节离线生成，不进服务依赖
- chat / completion 模型 SDK
- 代码生成类注解处理器
- 第三方 HTTP 客户端库

## 4. 接口契约

### 4.1 `POST /v1/enhance`

请求：

```
{
  "task": 字符串，1–4000 字
  "options": { "topK": 整数，3–26，默认 8, "budgetTokens": 整数，默认 400 }
  "traceId": 字符串，可选
}
```

响应（成功恒为 200）：

```
{
  "prompt": 字符串，永不为 null，未命中时为空串
  "traceId": 字符串
  "meta": {
    "action": "INJECT" | "FALLBACK" | "DEGRADED"
    "cardId": 字符串或 null
    "confidence": 数值 0–1
    "libraryVersion": 字符串
  }
}
```

**三条硬规则**

1. `prompt` 永不为 null。未命中返回空串——调用方可以无脑写「基础 prompt + 返回值」，不需要任何分支。
2. 降级也返回 200。对调用方来说「服务活着但这次没意见」远好于「服务挂了」。降级通过 `meta.action` 可观测，但不中断对方链路。
3. 相同任务 + 相同库版本 → `prompt` 逐字节相同。接口是纯函数。

**错误**：400（task 非法）、422（超长）、503（库未加载）。错误体 `{ "error": { "code": 字符串, "message": 字符串 } }`。

**其他端点**：`GET /healthz`（健康检查）、`GET /v1/cards`（列出模式库，用于确认加载了几张卡、库版本对不对）。

这两个端点是给运维和排查用的，不承担 UI 职责——本项目没有 UI。单卡查询端点不预留，需要时再加。

默认端口 18080。

### 4.2 调试参数 `override`

实验需要强制指定卡（随机臂、最佳单卡臂、标注真值臂）或不注入。为了让所有实验臂走**同一个接口**，加一个可选字段：

```
"override": { "mode": "forceCard" | "placebo" | "baseline" | "randomCard", "cardId": 字符串, "seed": 整数 }
```

只在配置开启时生效，生产默认关闭，且不出现在对外接口文档里。

**为什么非要这样**：如果实验臂另走内部调用路径，两套代码产出的结果就不可比，实验作废。

## 5. 数据契约

### 5.1 模式卡

一卡一文件，YAML，放在 `cards/<domain>/` 下。

**本质是"一段给模型看的工作流"**：告诉它按什么顺序想、容易在哪里翻车、什么时候该收手。

| 字段 | 说明 |
| --- | --- |
| `id` | 全局唯一，`域前缀-策略名` 形式 |
| `domain` | `planning` / `debate` / `general` |
| `name` | 卡片显示名 |
| `applicableWhen` | 中文 ≤ 80 字。**精判唯一可见的内容**。末尾必须带一句「不适用于……」 |
| `steps` | 4–6 条，每条一句话，是可直接执行的动作 |
| `failureModes` | 2–4 条，这类任务上模型最常翻的车 |
| `exitConditions` | 1–3 条 |
| `outputContract` | 期望的输出形态 |

一张卡的实际样子：

```yaml
id: debate-steelman-each
domain: debate
name: 逐方钢人化对比
applicableWhen: 立场分析、方案对比、论证评估，任务要求判断哪边更有理；不适用于只有单方观点或纯事实查证。
steps:
  - 为 A 方构造最强论证（不是稻草人）
  - 为 B 方构造最强论证
  - 找出双方论证依赖的关键前提差异
  - 评估哪些前提有证据支持、哪些是价值判断
  - 区分事实分歧与价值分歧，分别给结论
failureModes:
  - 双方论证强度不对等（一方被削弱）
  - 把价值分歧误判为事实分歧
exitConditions:
  - 分歧纯属价值判断时，不强行裁决，输出「取决于价值取向」并说明分歧点
outputContract: 分节输出 a_strongest / b_strongest / premise_gap / fact_vs_value / verdict
```

**两条写作要求**

1. **退出条件不只管"做完了"，更要管"该收手了"。** 好的骨架会在信息不足时明确指示停止并承认不确定——"分歧纯属价值判断时不强行裁决"、"假设无法区分时输出候选集而非强行选一个"，而不是逼模型硬给一个答案。这是注入骨架相对普通 CoT 最有价值的差别，写卡时要优先想这一条。
2. **"不适用于什么"必须写进适用条件里。** 决策模型是字面阅读，看不到未明说的边界；把负例写在同一字段既强迫作者想清近邻卡的差别，也让精判能据此排除。**不要拆成单独字段**——那样精判看不到，就成了不会被读取的悬空字段。

**核心约束：精判只看 `applicableWhen`。** 其余字段不进精判输入——决策模型有上下文稀释问题，无关长文本会降低判断质量。所以这一个字段必须能独立表达"这张卡什么时候该用"。

**域的划分与评测范围**（重要，决定工作量投向）

| 域 | 内容 | 是否纳入实验 |
| --- | --- | --- |
| `planning` | 约束规划（资源/时序/容量/互斥的排布） | **是**，主结果 |
| `debate` | 立场对比与论证评估 | **是**，泛化性验证 |
| `general` | 跨域通用策略，含**根因诊断**类（假设排除、证伪设计） | **否**，只建卡不评测 |

`general` 域的卡照写照维护，但不生成对应任务集、不参与对比实验。报告里要写明"该域已建卡但未纳入本轮评测"——主动划边界比被问出来强。

### 5.2 模式库版本

所有卡片文件按相对路径排序、内容归一化（行尾统一为 `\n`、去行尾空白）后拼接，取 SHA-256 前 12 位。

归一化那一步不能省：否则 Windows 与 Linux 会算出不同的版本号，"库变了就不许比"这条纪律自己就失效了。

### 5.3 任务集

JSONL，一行一任务：`taskId` / `domain` / `prompt` / `constraints` / `stances` / `acceptableCards` / `meta`。

`acceptableCards` 是**可接受集合**（1–2 张），不是唯一正确答案——同一个任务常同时适配两张卡，按单一正确答案标注会造出一批假错误。

**约束写成结构化判定器，不用自由表达式**

```
{ "cid", "type", "text", "params" }
type ∈ capacity | precedence | mutex | window | assignment | ratio
```

理由：自由表达式（如 `sum(line.output) <= 120`）要额外解决变量绑定、作用域、求值安全三个问题，而实际只需要这 6 种判定。

**planning 域的词汇必须统一**：`line`（产线，每日可用工时）、`order`（订单，所需工时/可做产线/最晚完成日）、`day`（第几个工作日）。模型输出 `assignments[{ order, line, day, startHour, hours }]`。任务描述、约束定义、模型输出三者用同一套名词。

### 5.4 输出格式

- `plan_v1`：`{ assignments[], verification[] }`
- `debate_v1`：`{ stances[{ label, thesis, evidence[], objections[], concessions[] }], verdict }`

这两个格式要写进注入文本的「输出格式」段，让下游能机械核验。注意：这不是我们校验模型输出的依据（我们不调模型），而是给调用方和实验侧用的。

### 5.5 审计

每请求一行 JSONL：召回候选、精判的选项顺序与概率分布、温度、门控动作、渲染结果、库版本。

**没有「理由」字段，也不要加。** 决策模型不生成文本，给不出理由。可审计的证据就是概率分布本身。

## 6. 几个踩过坑才定下来的决策

改之前先理解为什么。

**① 回退是一个可被选中的选项，不是"概率太低"**

决策模型的 Choice 是封闭集，它**必然**从候选里挑一个，哪怕全都不合适。两张烂卡 55/45 纠结时，它呈现为"中置信"，实质是"都不对"。所以在候选池里放一张虚拟卡（选项标为 `None`），让"都不合适"能被投出来。这样门控从阈值工程变成决策结构。

**② 精判选项用单字母 A–Z，卡片描述放输入正文里**

这类模型靠读预填位置的 logit 出概率，**多 token 标签会退化**。单字母是硬约束，直接导致 `topK` 上限为 26。

候选按 `cardId` 字典序映射字母，**不按检索分数**——分数会随 embedding 版本变化，按分数排会破坏可复现性。

**③ 置信度必须自己重新标定**

原始 logit softmax 校准很差（社区实测 ECE 约 0.47，温度拟合后降到 0.08）。不标定的话，阈值规则形同虚设。标定只在验证集上做，测试集只用于报告。

**④ 实验必须有 placebo 组**

"注入了针对性骨架"和"prompt 变长了"这两个因素必须分开。placebo 组用等长、同结构、但内容通用的假骨架。**本系统与 placebo 的差值才是真贡献**，和无注入组比会高估。

**⑤ 模式库 48 张，3 域 × 8 族 × 2 变体**

同族两张是**受控的近邻**：面对同一类任务，但骨架不同（全量 vs 增量、构造 vs 修复）。互不相干的卡会让"选哪张"变成简单题，失去难度。

粗筛 top-8 / 48 = 16.7% 保留率，这才是级联召回有意义的前提。**注意 `general` 域的 16 张卡虽然不参与评测，但它们仍在检索池里**——planning/debate 任务完全可能被误召回一张通用卡，这是真实存在的失败模式，要单独统计跨域误选率。

## 7. 实验设计

**要证明的**：在选定任务分布上，本系统显著优于无注入、固定单模式、随机召回。

**对比组**

| 组 | 内容 | 作用 |
| --- | --- | --- |
| baseline | 无注入 | 下界 |
| placebo | 等长通用骨架 | 剥离"prompt 变长" |
| random | 随机取一张卡 | 证明不是随便给张卡都行 |
| fixedBest | 固定注入验证集上最好的单卡 | 证明不是选一张好卡就够 |
| ours | 完整系统 | 主结果 |
| oursNoGate | 召回 top-1 直接注入 | 验证门控的独立价值 |
| oracle | 注入标注卡 | **上界**，定位瓶颈在召回还是在注入 |

**指标**：约束全通过率（主）、召回命中率、注入率、高置信档精度、校准误差、**跨域误选率**（planning/debate 任务却选了 general 卡的比例）、注入 token 数、延迟。

**消融**：逐项删除退出条件 / 失败模式 / 其中一个推理步骤 / 精判（召回 top-1 直接注入）/ 门控（全量注入）/ fallback 候选（改用阈值判断）。最后一组验证的是"回退作为可选项"这个设计的必要性。

**k 扫描**：`topK` 从 8 扫到 26，看召回是否损失信息。这一组用来回答"为什么不直接全库精判"——召回只会丢信息，不会增加信息，所以必须用数据说明它没丢多少。

**规模**：约 200 条任务。验证集 60（标定温度与阈值、选 fixedBest）、测试集 140（只用于报告）。

**不能破的纪律**

- 温度与阈值只在验证集上定，测试集只报告。同一份数据既调参又报结果等于自证
- 失败样本计入分母，不丢弃
- 所有臂走同一个 HTTP 接口
- 写卡的人不看任务生成器模板——否则卡片"知道答案"，增益是假的
- **实验执行器与服务进程分离**：实验脚本要自己调执行模型，但那份代码不进服务的运行依赖。服务的依赖树里不出现任何 chat / completion 模型 SDK——这是"我们不碰模型"的技术保险，靠依赖树而非承诺来保证

## 8. 交付物

可运行的后端服务（单 jar 启动即用）、48 张模式卡、任务集与生成器、实验脚本与结果数据（JSON / CSV）、实验报告。

不做演示页面。项目的说服力由两样东西承载：接口本身能不能用，以及实验数据站不站得住。
